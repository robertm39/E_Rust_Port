# Preregistration: preprocessing evaluation

Bead: `E_Rust_Port-9jt.7.1`

Date frozen: 2026-07-29

## Question

Do any of Umlaut's existing, default-off blocked-clause or
definition-oriented preprocessing passes have enough safe held-out reach and
end-to-end benefit to justify a generated-schedule follow-up?

## Static decision before measurement

The source inventory was completed before benchmarking. Formula definition
introduction, equation-definition unfolding, blocked-clause elimination,
singular predicate elimination, goal definitions, SInE, relevance pruning,
formula splitting, and FOOL/ITE/LET/lambda lowering are already
production-connected. The generated schedules enable none of BCE, predicate
elimination, predicate gate recognition, or goal definitions.

No new logical transformation will be prototyped. The experiment instead
adds additive, opt-in telemetry that distinguishes:

- clauses removed by blocked-clause elimination;
- clauses removed and generated by predicate elimination; and
- goal-definition clauses added.

This is measurement instrumentation only. All production defaults and
generated schedules remain unchanged during the experiment.

## Strategies

Every strategy uses the same fixed search controls:

- `--expert-heuristic=(5*Refinedweight(ConstPrio,2,1,1.5,1.1,1.1),1*FIFOWeight(ConstPrio))`
- `--term-ordering=KBO6`
- `--forward-demod-level=2`

The four candidate-blind variants are:

1. `baseline`: no extra option;
2. `bce`: `--bce=true`, retaining the production occurrence limit of 512;
3. `predicate`: `--pred-elim=true`, retaining the production occurrence
   limit 512, tolerance 0, no gate recognition, no forced mu decrease, and no
   conjecture-symbol exclusion; and
4. `goal_defs`: `--goal-defs=All`, without recursive subterm definitions.

No combined strategy is evaluated because it would prevent attributing
growth or reduction to one pass.

## Correctness and provenance gates

Before performance interpretation:

1. all existing BCE, predicate-elimination, goal-definition, definition
   unfolding, formula-CNF, SInE, splitting, and proof-output tests must pass;
2. focused end-to-end tests must report exact telemetry counts for each
   evaluated pass;
3. rule-specific semantic/property tests and proof metadata must remain
   intact: BCE archives deleted originals, predicate resolvents retain
   `DC_PE_RESOLVE`, and generated goal definitions retain `DC_INTRO_DEF`;
4. all build-paired terminal statuses must have the same proof/model polarity;
   and
5. at least one reproducibly solved, transformed proof for each candidate
   that yields one must pass the integrity-pinned ProofCheck 1.0 path. If a
   candidate transforms no successful proof, the focused ancestry test is the
   explicit proof-coverage boundary.

Any failure makes that candidate inconclusive and forbids a schedule change.

## Frozen workloads

### Candidate-blind held-out phase

Reuse the exact 20-problem CASC-2025 test selection and corpus hashes frozen
in `../2026-07-29-014-rewrite-cache-evaluation/corpus.json`. The source
manifest SHA-256 must remain
`31c9a99e4b34b56352b3311f3efe5c97f728fd078783085e1811d83eec271f6d`.

Each of 20 problems runs under all four strategies, twice, with a 10-second
soft and 13-second hard CPU budget. This produces 160 held-out runs.

### Differential phase

The three tracked inputs under `targeted/` are fixed before execution. Each
runs under all four strategies, twice, with a 5-second soft and 8-second hard
CPU budget. This produces 24 runs. The phase verifies that each option's
telemetry can distinguish enabled-and-fired, enabled-but-inapplicable, and
disabled behavior while preserving the expected unsatisfiable status.

The differential phase establishes behavior and proof coverage only. It may
not supply solve or performance evidence for promotion.

## Execution and analysis

All Rust builds, tests, prover runs, and benchmarks execute on one ephemeral
Ubuntu 24.04 Linode through `linode-runner.ps1`. At most four jobs run
concurrently with 1536 MiB per job. Contracts retain source revision, binary
hash, manifest and problem hashes, exact commands, host metadata, stdout,
stderr, telemetry, and proof objects. Job order is deterministically hashed,
and a second unchanged invocation must resume every coordinate.

Analysis reports for each strategy:

- reproducible solve set and unique solves;
- exact status and polarity disagreements;
- transformation-active problems and repetitions;
- removed, generated, and added clause totals;
- common-solved CPU, generated, processed, high-water, term-storage, and RSS
  ratios relative to baseline; and
- proof-validation coverage and regressions.

Timeout-limited all-run resource totals are diagnostics, not speedups.

## Candidate decisions

Each option is decided independently against baseline.

Open a generated-schedule follow-up only if correctness passes, the option
causes a transformation on at least four held-out paired coordinates, it has
no baseline-only reproducible solve, and either:

- it has at least one candidate-only reproducible solve; or
- on common reproducible solves, median CPU is at most `0.95`, generated and
  high-water ratios are at most `1.02`, and maximum-RSS ratio is at most
  `1.05`.

Retain the option as explicit default-off compatibility behavior when it
fires on fewer than four held-out paired coordinates, adds no unique solve,
or fails the benefit gate without a material regression.

Reject a generated-schedule follow-up when correctness passes but the option
loses a reproducible baseline solve, or common-solved CPU, generated,
high-water, or maximum RSS exceeds `1.05`.

Any invalid proof, polarity disagreement, source/binary mismatch,
nondeterministic resume, or malformed telemetry is inconclusive and leaves
the production default off.

No post-hoc workload or threshold may affect these decisions. Exploratory
diagnostics must be labeled separately.
